# 缺陷单输出与提交

默认生成新的 issue-draft.md，已有草稿只按用户要求更新。一段视频展示多个独立缺陷时分别成单，相关现象可用同一时间线关联，避免将猜测拆成大量 Issue。

## 草稿模板

```markdown
# [模块] 条件下出现的具体异常

- 状态：草稿 / 待补信息 / 已提交（仅平台确认后）
- 环境与构建：已知值；未知项明确列出
- 前置条件：视频可见或用户提供的账号角色、状态
- 复现情况：录屏观察；是否另行复现、尝试次数均据实填写

## 复现步骤
1. 可观察动作，附必要时间戳。

## 预期结果
需求、验收规则或用户说明及其出处；未知则待确认。

## 实际结果
可见异常、开始/结束时间和是否恢复。

## 证据
视频标识、审阅区间、关键时间戳/帧、采样与观察限制。

## 影响与建议严重程度
已观察影响及建议依据；平台 priority 仅按该项目规则填写。

## 待补充信息
只列影响复现、判定或平台提交的缺口。
```

“疑似卡住”不能自动改成“服务端死锁”；缺少预期时不根据现有实现编造需求。单次观察写“视频出现一次”，不能填“必现/100%”。记录者补充的信息与视频事实分开标注。

## 平台提交

从用户要求确定平台、项目/仓库及 Issue 类型，读取当前连接器的字段要求。已有明确授权和目标时继续提交，无需重复确认；单纯“整理/生成 Bug”不代表要求外发。缺失平台必填字段先完成草稿，再请求具体缺失信息，不填假值。

附件只上传本次缺陷所需且获准的脱敏视频/帧；本地绝对路径不是接收者可访问的附件链接。保留源视频，脱敏副本单独关联。没有附件上传能力时交付草稿和本地证据位置，明确附件尚未上传。

创建请求超时或返回不确定时先查询是否已创建，避免重复提交。用平台响应或读取结果核实标题、项目、ID 和 URL；未确认成功时不得标已提交或编造链接。后续补充已有 Issue 应使用其真实 ID，不重新创建重复问题。
