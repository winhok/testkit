# 将缺陷录屏整理为问题单

`video-to-issue` 将应用或网站录屏整理成可提交的 Bug/Issue 草稿，提取可见操作、页面状态、异常时间线、复现步骤、预期与实际结果、环境信息和时间戳证据。

## 工作方式

1. 核对视频来源、时长、帧率或时间基准，以及是否有音轨。
2. 短视频完整审阅；长视频先粗定位，再加密异常前后区间。
3. 记录用户操作、状态变化、异常起止和恢复情况，并引用具体时间戳。
4. 生成 `issue-draft.md`，保留无法从视频确认的信息。
5. 只有用户明确要求提交并指定平台/项目后，才调用已连接工具创建问题。

默认草稿包含：

- 标题、环境和构建信息。
- 前置条件和编号复现步骤。
- 带来源的预期结果与视频可见的实际结果。
- 时间戳、关键帧、影响和待补信息。

典型请求：

```text
把这段 Android 缺陷录屏整理成 Bug 草稿，标出异常时间戳
根据视频生成 GitHub Issue，但提交前先让我确认内容
```

## 证据边界

- 复现步骤只写视频可见或用户明确补充的动作。
- 一次录像不代表已经独立复现，也不能证明网络、数据库或代码级根因。
- 没有需求依据的预期结果会标记待确认。
- 不编造复现率、严重程度、设备版本、根因或平台 Issue ID。
- 视频时间和日志墙钟时间需要另行校准；语音仅在相关时转录，不默认 OCR 全部帧。

用户只要草稿时不会外发；缺少平台、项目、必填字段或连接工具时也只保留草稿。完整执行契约见 [`video-to-issue`](../skills/video-to-issue/SKILL.md)。后续独立复现和修复复测使用[缺陷验证](defect-verification.md)，服务端根因分析使用[日志分析](log-analysis.md)。
