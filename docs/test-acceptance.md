# 验收测试结果与证据

`test-acceptance` 根据已确认的版本、冻结测试范围、执行结果和证据覆盖形成可复核的验收结论，识别漏测、阻塞、证据过期和未满足的退出条件。

## 支持的工作方式

- **计划正式验收**：读取当前 TestSpec requirements、strategy、cases 和 review，确认构建、环境、必测范围与退出规则后冻结范围。
- **检查已有执行**：验证 scope、全部 attempts、原始证据和当前目标版本，再计算结论。
- **只整理报告**：保留已有状态，不发起执行、不改变冻结范围、不改判。
- **迁移旧报告**：先检查再输出新文件；历史成功不会自动成为当前验收通过。

## 需要的输入

- 需求和用例版本，或明确的局部检查目标。
- 被测构建、环境、账号角色和目标组合。
- 冻结范围及 required/optional 检查。
- 每次执行尝试、原始结果、截图或其他证据。
- 清理要求、重试记录和退出条件。

## 结论如何形成

共享验证工具会计算 required checks 的覆盖、执行状态、证据合法性和 `acceptance_status`。报告列出通过、失败、漏测、阻塞、跳过、清理、重试及证据限制，不用总通过率掩盖关键用例遗漏。

局部 scope 只能说明局部检查，不能称整个版本通过。源需求、用例内容或被测对象变化后，旧结果保留为历史事实并标记 stale；只有重新冻结和执行受影响范围，才能形成新的当前结论。必要断言证据不足时给出 `inconclusive`。

典型请求：

```text
检查本次冻结范围是否全部执行，并列出阻塞和证据缺口
只汇总现有报告，不要补跑测试，也不要改变原结论
判断这些旧报告能否支持当前候选构建验收
```

测试验收不代表生产已发布，TestLib 入库也不代表测试通过。完整执行契约见 [`test-acceptance`](../skills/test-acceptance/SKILL.md) 和[共享执行契约](../skills/_test-run-shared/references/execution-contract.md)。

再验收可通过 defect.json.lineage 追踪来源失败、缺陷复测和新验收运行。工具保留来源全部必测检查，重新计算新范围的结果，并分别报告缺陷 verified 与再验收状态；两者都满足时才列出已关闭的来源检查。只整理报告不触发新的执行或补造关联。详见[缺陷关联契约](../skills/defect-verification/references/retest.md)。
