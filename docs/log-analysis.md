# 分析服务端日志

`log-analysis` 将应用日志、JSON/structured log、HTTP/access log、数据库慢查询、消息队列、定时任务、网关和系统组件日志还原为可读链路，用于定位失败、超时、慢调用、字段丢失、数据不一致、重试降级和日志质量问题。

## 可以提供什么

- 直接粘贴的日志片段。
- 当前工作区中的日志文件或指定行范围。
- `rg`、`zgrep`、`jq` 等命令的过滤结果。
- 日志平台查询结果，以及 traceId、requestId、业务 ID 或时间窗口。

远程服务器路径不能被当前环境自动读取时，需要先导出或粘贴相关片段。大日志优先按关联 ID、业务 ID、服务和时间窗口收敛，而不是全量扫描。

## 分析模式

| 需求 | 处理方式 |
|---|---|
| 某接口为什么慢或失败 | 聚焦相关链路，先给结论，再给证据 |
| 字段为空、丢失或不一致 | 沿入口、服务、存储、消息和响应逐跳溯源 |
| 少量日志，没有明确问题 | 快速概览链路与异常 |
| 多服务、多链路或复杂日志 | 深度诊断拓扑、耗时、依赖、重试和日志质量 |
| 怎么搜 trace、查询太慢或搜不到 | 设计带时间窗和字段约束的最小查询方案 |

典型请求：

```text
分析 app.log 中 traceId=1234567890123 为什么超时
对比入口和下游日志，找出 user_type 在哪一跳变成空值
这条 Loki 查询为什么结果太多，给我一个更小的检索方案
```

## 输出原则

报告会区分日志事实、推断和无法证明的部分。关联优先级依次是 trace/correlation/request/span ID、线程或任务上下文、业务实体 ID，最后才是时间邻近。没有日志不等于没有收到字段，HTTP 200、`SUCCESS` 或没有 `ERROR` 也不等于业务逻辑正确。

证据不足时只给少量、带目的说明的深挖命令，并限制时间、文件和查询范围。敏感值只保留定位问题所需的最小信息。
