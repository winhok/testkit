# k6 适配参考

使用原生 JS/TS 资产及实际安装版本。协议测试为常规入口；浏览器指标仅在任务需要时加入，不强制 browser、Node、Playwright 或云执行。

## 负载与脚本

- constant-vus/ramping-vus 对应 closed 模型；constant-arrival-rate/ramping-arrival-rate 对应 open 模型。rate 计业务 iterations/timeUnit，不是 HTTP RPS。
- open 计划明确 preAllocatedVUs、maxVUs、timeUnit、阶段和停止策略。高延迟时所需 VU 会增加；记录 dropped_iterations，不能用低延迟掩盖未启动负载。
- arrival-rate executor 自己调度迭代，不机械在迭代末尾加 sleep 控制速率；真实业务步骤的 think time 按计划保留。
- 业务步骤按成功路径关联变量；用稳定 tags/name 控制标签基数，避免完整订单 ID、token 或业务正文进入指标。
- checks 验证单次业务正确性，但失败本身不保证进程非零；明确 checks/business completion 的 thresholds 或执行后评估，保留 HTTP 失败与业务失败的区别。
- 请求延迟与迭代/旅程时间分开。`http_req_duration` 包括发送、等待、接收，不含初始 DNS/TCP/TLS 连接时间；需要端到端口径时单独采集，不直接对照 JMeter elapsed。
- 数据唯一性考虑每 VU/每迭代/分布式分片。setup/teardown 不是每 VU 自动执行的初始化/回收；异常中止后核对实际清理。
- secret 使用 `__ENV` 等已确认安全机制；阈值、负载与非秘密 override 入 manifest/effective config，不保存真实 env 值。

## 执行与结果

```sh
k6 run --out json=<new-run>/raw/metrics.json <script.js>
```

JSON 时间序列输出和自定义 handleSummary 各有用途；按安装版本配置需要的 percentile 与 summary。不能只保存终端摘要就声称拥有阶段、业务完成、原始分布或全部 VU 证据。
threshold 失败导致非零退出，脚本/工具错误也可能非零，原生原因分别保存。abortOnFail/延迟评估策略来自冻结计划，中止要记录时间、原因和 interrupted/dropped。
云和分布式为条件能力，单独核对费用/目标/数据范围授权；local 验证通过不代表 cloud 可用。不自动采用第三方 URL 或云上传。
